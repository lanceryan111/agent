# 初次落地后的优化计划

本计划以 Copilot 配置落地为主；末尾也包含应用初次部署后的优化流程。周期是建议节奏，不是自动执行或定时任务。负责人角色由团队指定，不假定现有组织结构。

## 第 1 阶段：打通开发与排障（第 1–3 天）

负责人：仓库维护者与使用者。

- 合并配置，保留已有组织规则；核对 instructions 匹配真实目录、skills 能被发现、agent 的有效工具与角色一致。
- 补齐 repo-map 的真实路径、Java/Spring 版本、build wrapper、测试入口、部署入口与配置来源。
- 选一个低风险 Java 功能改动和一个已知故障，分别用 Build 与 Diagnose 完成。代码必须经现有检查和人工验收。
- 输出：合并后的配置、真实仓库地图、两份任务记录。
- 通过条件：可以定位正确模块，完成实际改动和验证；只读角色未产生编辑/执行；没有把未执行检查写成通过。发现不符合时先修配置，不急于增加技能。

## 第 2 阶段：建立质量与费用基线（第 1 周）

负责人：使用者与评审者。

- 收集 5–10 个代表性任务，覆盖功能、重构/测试、故障和交付配置。
- 使用 evaluation-template 记录验收通过、人工返工、耗时、可归因的 credits 和后续缺陷。
- 同模型对比旧/新配置；同配置再对比公司可用的较低成本模型与常用强模型。使用隔离会话/分支和相同起点，避免前一次修改污染后一次。
- 输出：基线表与主要失败类型：检索错误、缺少项目事实、设计误解、实现缺陷、无效验证或工具不可用。
- 通过条件：知道主要质量损失发生在哪里，费用能被合理归因。尚不能归因时先解决观测，不据单次账单下结论。

## 第 3 阶段：针对失败优化（第 2 周）

负责人：配置维护者。

- 检索错误：补入口/路径并修匹配范围；不要直接扩大到全仓库常驻上下文。
- 反复误解项目：加入一条有证据的项目事实，并引用来源。
- 反复采用错误流程：修对应 skill；只在确有重复工作时增加技能。
- 重复手工操作：把已有验证流程固化为仓库脚本或任务，输出精简结果和完整日志位置；先验证脚本本身。
- 无效测试：加入可观察验收样例，检查测试是否能捕获缺陷。
- 循环消耗：限制范围、重试和输出；检查工具是否返回大量无关内容。
- 每次只改变一个主要因素，重跑受影响的案例。
- 输出：经案例证明有效的规则/脚本变更与复测结果。
- 回退条件：验收质量或人工返工明显恶化且无可接受收益时，恢复上一配置版本。

## 第 4 阶段：模型分工与推广（第 3–4 周）

负责人：使用者、仓库维护者；涉及预算时由相应管理员参与。

- 为简单实现/测试、复杂跨层诊断、方案比较选择各自能稳定通过验收的最低总成本模型。
- 保留强模型升级条件：跨模块兼容性不确定、证据矛盾、常规模型在补齐证据后仍失败。不要无证据地不断换模型。
- Review 用于复杂或高影响变更；小改动不强制 Build → Review → Optimize 全链路。
- 删除重复和无效果规则；把长的条件流程移到按需 skill。
- 只有当现有记录证明外部运行证据缺失是瓶颈时，再评估公司允许的 Actions/观测平台等连接；不默认全开工具。
- 输出：模型使用表、维护责任人、配置回退版本与精简后的规则集。
- 通过条件：在验收质量不降低的前提下，总耗时、返工或每个成功任务的 credits 至少一项得到可重复改善。

## 后续维护（建议每月或版本变化后）

复测固定案例；检查仓库地图和匹配路径是否失效；复查模型价格/可用性；删除过时规则。50,000 credits 的额度周期和归属确认后再设预算预警，不将本计划视为已设置的平台硬上限。

## 如果“初步部署”指业务应用上线

使用 DevOps Optimize + post-deploy-review，以证据建立应用优化 backlog：

1. 首次部署后：核对版本/镜像、关键业务路径、错误和延迟，以及已有回滚路径。数据窗口由业务流量与现有目标决定。
2. 建立代表性基线：关键接口延迟/错误、JVM 与容器资源、依赖耗时、CI/CD 耗时；只收集相关项。没有业务目标时先定义目标，不猜 SLO。
3. 选择影响最大且证据充分的 1–3 个问题，写成下表。
4. 在授权测试环境实施最小实验；通过验证后按团队既有流程部署。比较相同或可比负载，明确是否改善及是否引入回归。
5. 保留、调整或回退；再处理下一项，不同时盲调 JVM、Pod 资源和线程池。

| 优先级/负责人 | 问题和证据 | 基线/目标 | 假设与改动 | 验证窗口/工作负载 | 风险/回退条件 | 实测结果 |
|---|---|---|---|---|---|---|
| 待评估 | 待采集 | 待确认 | 待证据支持 | 待确定 | 待确定 | 未执行 |

这里提供流程，不声称你的应用存在任何性能瓶颈，也不预设可节省比例。
